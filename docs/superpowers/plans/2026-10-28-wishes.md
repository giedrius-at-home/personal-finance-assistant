# Wishes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Wishes tab where the owner plans purchases (with optional sub-wishes) and sees, month by month, whether each is affordable and what has to give: savings, budget groups by importance down to their floor, or the credit card charged next month.

**Architecture:** Wishes and card settings are stored as JSON payload rows in two new tables (new storage migration). A pure core engine turns stored wishes into per-month demands (`schedule`), builds per-month baselines from the dashboard's `CurrencyAllocation` (`baseline`), and runs the cutting ladder across months (`ladder`). `Service::wishes()` assembles a `WishesView` from the dashboard. Writes go through the existing `Writer`. Marking a wish bought writes the cuts it needed into that month's `BudgetPlan`.

**Tech Stack:** Rust, rusqlite, rust_decimal, jiff, Tauri commands, Leptos UI (wasm).

**Spec:** `docs/superpowers/specs/2026-10-28-wishes-design.md`

## Global Constraints

- Card limit default **€2,500**, editable. Card balance is charged in full on the 1st/2nd of the following month.
- Ladder order, fixed: (1) month's free money, never below 0 → (2) budget groups with an importance, highest number first, each down to `max(floor, already spent)` → (3) credit card up to free limit → (4) short by N.
- Groups with no importance are never cut. Importance 1 = protect most.
- A wish whose source is the card goes onto the card first (up to free limit); any remainder runs steps 1, 2, 4.
- Wishes in a month stack, in this order: card charge from previous month, set-asides, then wishes due that month by `due_on`, then `created_at`.
- Sub-wishes: one level only. Sum of sub-wishes may not exceed the parent cap (warn, don't reject). Implicit "rest" = cap − sub-wishes (bought ones at actual amount), due on the parent's date.
- Saved money is entered by hand and taken off month 0's free money (earmarked).
- Cuts change the stored `BudgetPlan` only when a wish is marked bought.
- No AI, no bank connection for the card, no money movement.
- CI: `cargo fmt --all --check`, the clippy commands in `.github/workflows/ci.yml` with `-D warnings`, and `cargo test --locked -p finance-types -p finance-storage -p finance-core` plus `cargo test --locked -p finance-ui --bins`.
- Money is `rust_decimal::Decimal`, rounded to cents (`round_dp(2)`) wherever a value is split.

## Review Focus

1. **Stale card number.** `card_used_month` is before the current month: treat month-0 usage as 0, flag `card_stale = true`. Test: `stale_card_usage_counts_as_zero` (Task 4).
2. **Wish dated in the past and still planned.** It counts as due in month 0, not dropped. Test: `overdue_wish_is_due_now` (Task 3).
3. **Group already overspent.** Cut room is `limit − max(floor, spent)`, never negative. Test: `overspent_group_gives_no_room` (Task 2).
4. **Card charge that next month cannot absorb** rolls through the same ladder (may go on the card again) and never vanishes. Test: `unpaid_card_charge_rolls_forward` (Task 2).
5. **Sub-wishes over the cap, or a parent with no sub-wishes.** Over cap gives `over_cap = true` and rest 0. No sub-wishes means the whole cap is the rest. Tests: `over_cap_flags_and_rest_is_zero`, `parent_without_children_is_all_rest` (Task 3).

### Task 2: The cutting ladder

**Files:**
- Create: `crates/core/src/wishes/ladder.rs`

**Interfaces:**
- Consumes: `Verdict`, `Cut`, `WishMonth` (Task 1).
- Produces:
  ```rust
  pub struct GroupRoom { pub id: String, pub name: String, pub importance: u8, pub limit: Decimal, pub min: Decimal /* max(floor, spent) */ }
  pub struct MonthBaseline { pub month: Date, pub free: Decimal, pub groups: Vec<GroupRoom>, pub card_used: Decimal }
  pub struct Demand { pub wish_id: Option<String>, pub label: String, pub amount: Decimal, pub on_card: bool }
  pub fn judge(months: &[MonthBaseline], demands: &[Vec<Demand>], card_limit: Decimal) -> Vec<WishMonth>
  ```
  `demands[i]` belongs to `months[i]`, already ordered. For `i >= 1`, `judge` itself puts a card-charge demand first (`wish_id: None`, label `"Credit card"`, amount = month `i-1`'s final `card_used`, `on_card: false`) when that amount is > 0. Group limits carry the cuts of earlier demands in the same month. Months do not share group cuts.

  Per demand, in order: if `on_card`, put `min(amount, card_limit − card_used)` on the card. Then the remainder goes through free money (`min(rem, free.max(0))`), then groups sorted by importance descending then name, each giving `limit − max(min, limit_after_earlier_cuts)` clamped ≥ 0. Then the card (only if `!on_card`). Then `short`. Merge repeated cuts of one group within a demand into one `Cut`.

### Task 3: Wishes to monthly demands

**Files:**
- Create: `crates/core/src/wishes/schedule.rs`

**Interfaces:**
- Consumes: `Wish`, `WishStatus`, `WishSource` (Task 1); `Demand` (Task 2).
- Produces:
  ```rust
  pub struct Planned { pub wish_id: String, pub label: String, pub due: Date, pub remaining: Decimal, pub on_card: bool, pub created_at: String }
  pub struct Family { pub parent_id: String, pub rest: Decimal, pub over_cap: bool }
  pub fn plan_items(wishes: &[Wish], current_month: Date) -> (Vec<Planned>, Vec<Family>)
  pub fn demands(items: &[Planned], current_month: Date, months: usize) -> Vec<Vec<Demand>>
  pub fn horizon(items: &[Planned], current_month: Date) -> usize   // 2..=24 months, covers the latest due month
  pub fn earmarked(wishes: &[Wish]) -> Decimal                     // sum of `saved` over Planned wishes
  ```
  `plan_items` skips Dropped and Bought wishes. Every planned leaf (a single wish or a sub-wish) becomes `remaining = (amount − saved).max(0)`. A parent becomes its implicit rest item (wish_id = parent id, label `"<name>: rest"`, `remaining = (rest − parent.saved).max(0)`, due = parent `due_on`, source = parent source), where `rest = cap − Σ planned sub-wish amounts − Σ bought sub-wish actual amounts`. A negative rest sets `over_cap = true` and rest 0. Due dates before `current_month` clamp to `current_month`.

  `demands`: for each item, `n` = months from `current_month` to the due month, inclusive. Set-asides of `remaining / n` (cents; the due month takes the remainder) go in each earlier month (`on_card: false`, label `"Saving for <label>"`). The due-month portion keeps the item's `on_card`. Each month's order: set-asides first, then due items by due date, then `created_at`.

                   settings: &WishSettings, earmarked: Decimal, months: usize) -> (Vec<MonthBaseline>, bool /* card_stale */)

  - `wishes_view`: currency = the allocation whose code is `"EUR"`, else the first. With no allocation, return a view with no months and every wish unjudged. Run `plan_items`, `horizon`, `demands`, `baselines`, `judge`. Then build `WishRow`s: each wish's verdicts are those whose `wish_id` matches it; a parent's row sums its children and its rest; `monthly_set_aside` = its month-0 set-aside demand.
